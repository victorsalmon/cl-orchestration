## Red lines

- **Never dispatch attached when the work must outlive the chat.** Detached
  or dead on the next message.
- **Never block the chat on a worker.** Return control; handle completions as
  events.
- **A detached worker has no human.** No questions, no inline interactive
  steps, `question` tool denied.
- **Never dispatch without an explicit, valid `provider/model`.** Fleet
  default is `opencode/opencode-go/deepseek-v4.1-flash` (thinking low; high only for complex logic) unless the
  operator names another.
- **Never spawn past a key set's cap.** Acquire a slot from
  `agent-spawn-capacity` before every spawn — attached or detached — and
  Release it when the worker ends. The caps are operator decisions, not
  defaults to re-derive: opencode-go 6 (both routes share one wallet), gemini
  4, devin 2, codex 8 fix/code-refactor + 4 recon. A refusal means *queue the
  work*, never "retry until it fits".
- **One writer per worktree**; never overlap two workers' write paths; never
  run parallel full test batteries on one repo.
- **Never accept a worker's report as verification.** Confirm commits, gates,
  tree state yourself.
- **Never let a worker force-push, rewrite history, or commit secrets.**

## Unattended reboot (daemon before login)

Agents survive a reboot only if the **daemon** comes back with nobody logged
in. The mechanism on this box is the boot-triggered scheduled task
`\Paseo Daemon`:

| Property | Value | Why |
| :--- | :--- | :--- |
| Trigger | `MSFT_TaskBootTrigger` | fires at boot, not at logon |
| Principal | operator account, `LogonType S4U`, `RunLevel Limited` | runs before interactive sign-in with no stored password. Local profile files are available. Windows-authenticated network shares and EFS files require a different logon type. |
| Action | `Start-PaseoBootDaemon.ps1` → `paseo daemon run --home <PaseoHome>` | Task Scheduler owns the foreground process. The launcher reloads the active keys from User scope before each daemon start. |
| Settings | `IgnoreNew`, restart 3x/1min, no time limit | no duplicate daemons, crash recovery |

Rules that keep this working:

- **`daemon run`, never `daemon start --foreground`.** `--foreground` was
  removed in Paseo 0.14.x; the old task exited 1 and nobody noticed because the
  desktop app started its own daemon at logon. A `desktopManaged: true` daemon
  dies with the GUI, so it is not evidence that reboot survival works.
- **Check the registered task with `-Verify`.**
  `vendor/cl-orchestration/cl-paseo/scripts/Fix-PaseoBootTask.ps1 -Verify` prints the registered
  action, principal, watchdog settings, last run result, and whether a daemon
  answers. Registration needs elevation (the task file grants the operator
  account read-only). `-RunNow` rehearses the launch when no daemon is
  already listening.
- **S4U is session 0: no interactive desktop.** Headless agent CLIs
  (opencode, codex, devin) run fine; anything that needs a window station —
  Paseo browser tools, Jev, Electron webviews, headed Playwright — fails until
  a human logs in. Never route a pre-login job through a browser.
- **A reboot kills running agents.** The daemon returning does not resume them.
  Commit or push their work first, then let `auto-resume` re-drive what was
  interrupted.
- **Check the boot blockers once per hardware/OS change:** BitLocker without an
  auto-unlock protector, a BitLocker recovery prompt, or a BIOS/Windows-update
  stage that waits for input all stop the machine before the task can fire.

## Resuming agents the reboot killed

Install the daemon, deterministic boot resume and watchdog from an elevated
PowerShell 7 session under the same Windows account as Paseo:

```powershell
& "$env:CL_REPOS_ROOT\cl-common\vendor\cl-orchestration\cl-paseo\scripts\Fix-PaseoBootTask.ps1" -WithResumeTask -WithWatchdog
```

This updates the tasks without restarting a running daemon. At the next boot,
check that the first line of `~/.paseo/daemon-boot.log` records Windows session
0 before the first interactive sign-in. Check `~/.paseo/resume-boot.log` for
the accepted `Continue` requests, and verify an interrupted agent produced a
new response. `-RunNow` with the daemon stopped rehearses the scheduled-task
launch without rebooting. A real reboot also exercises disk availability and
the boot trigger.

### Key Check watchdog and alerts

`Paseo Key Check Watchdog` runs every five minutes independently of the desktop
app. It restores a missing watch, checks the daemon and OpenCode provider,
and records the latest outcome in
`~/.machine/state/key-check/paseo-watchdog.json`. It warns below 2 GiB free
on the OpenCode volume. Key Check refuses to switch below 500 MiB free.
`Paseo Key Check Alert` shows actionable failures in the interactive Windows
session and on sign-in. Failures are also written to the Application log
under `Paseo Watchdog`. For planned maintenance, temporarily disable the
watchdog task so it does not restart the daemon.

The cutover checks that the original processes exited and that the listener
was released. It retries shutdown through Paseo when it can still identify
the original daemon. If the same process still holds the listen socket after
that attempt, the watchdog asks the operator to restart Windows. The key
change and agent roster are journaled on disk. The next boot tries to verify
the applied key and resume that roster before running another cutover.

For alerts while signed out or when Windows cannot run its tasks, configure a
Healthchecks-compatible HTTPS ping URL as the operator's User-scope
`KEY_CHECK_HEALTHCHECK_URL`. Set the external receiver to expect one ping
every five minutes with at least ten minutes of grace and choose its alert
destination. The watchdog posts `/fail` for a confirmed incident and sends a
success ping when healthy. The external receiver detects missed pings. Keep
the URL private and record changes in the credential audit.

The daemon coming back does **not** continue interrupted work, but nothing is
lost. Each agent is a JSON record at
`<home>/agents/<workspace>/<agent>.json` carrying `lastStatus`, `lastActivityAt`
and `persistence.sessionId` (the provider-native session). Resume means
re-sending a turn, not re-dispatching:

```
paseo send <agent-id> "Continue"      # re-attaches persistence.sessionId
paseo agent reload <agent-id>         # restarts the underlying process instead
```

There is no `resume` verb and no "resume everything" command. The classifier
(shared with `Skills/auto-resume`): `running` while the daemon does not report
it running, or `error` with no `requiresAttention`, is *interrupted*; `idle`,
`closed`, archived, and stale records are left alone.

`vendor/cl-orchestration/cl-paseo/scripts/Resume-PaseoAgents.ps1` implements that rule and is
registered as the companion task `Paseo Boot Resume` (boot + 2 min delay,
S4U, logs to `<home>/resume-boot.log`). `-DryRun` prints the plan; the fixture
test is `-PaseoHome <fixture> -SkipDaemonWait -DryRun`.

Proven on this box (2026-10-31): a probe agent was interrupted mid-turn with
`paseo stop`, then `paseo send <id> Continue` re-attached the same provider
session and the agent re-ran the aborted command on its own. So `Continue` is a
real resume, not a fresh dispatch.

Two behaviours to know:

- **A graceful `stop` writes `lastStatus: idle`; a hard kill leaves `running`.**
  That is why the classifier resumes only `running`-but-not-live records — an
  agent you deliberately stopped stays stopped.
- **Resume is a new turn.** In-flight tool calls and half-written files are not
  restored. Commit before rebooting instead of relying on this.

Safety caps (do not remove them): `-MaxResumes` 12 and
`-BetweenResumesSeconds` 20. A provider key set has a hard concurrency cap
(opencode-go 6); an instant burst of `Continue` turns trips 429s and burns the
wallet. "Resume everything not archived" is **not** a safe instruction — this
home holds 1441 agent records, 1141 of them closed; the reconciler deliberately
resumes only the interrupted, recent subset.

List-then-send, when you want to see the set before it fires:

```powershell
# phase 1 - list only, changes nothing, writes the reviewed set
.\Resume-PaseoAgents.ps1 -DryRun -Manifest ~\.paseo\resume-manifest.json
# phase 2 - send to exactly that list (re-classification skipped)
.\Resume-PaseoAgents.ps1 -FromManifest ~\.paseo\resume-manifest.json
```

Why the list is read from `<home>/agents/**/*.json` and not from `paseo ls`:
after a restart the daemon reports an interrupted agent as `idle`/`closed`,
identical to one that finished normally. `lastStatus` on disk is the only
surviving marker of "was mid-turn", so the CLI alone cannot build a correct
list. `paseo ls --json` is still used, but only to subtract agents the daemon
is genuinely running right now.

Two trigger shapes, one decision:

| Shape | Command | Use |
| :--- | :--- | :--- |
| Deterministic script (default) | `Fix-PaseoBootTask.ps1 -WithResumeTask` | mechanical resume, no tokens, auditable log |
| Agent in the loop | `Fix-PaseoBootTask.ps1 -WithResumeTask -DispatchAgent` | judgement needed: re-dispatch vs continue, provider-error triage; dispatches `auto-resume` with `paseo run --no-wait` |

Still no native "run this agent when the daemon starts": schedules are cron
only and plugins have no daemon-start event. **Operator decision
(2026-10-31): no periodic resume schedule.** The boot reconcile is the only
resume trigger; do not add a recurring resume schedule without asking. A daemon
restart that is not a reboot (e.g. `paseo restart`, or the GUI taking over the
daemon) is resumed by hand with `Resume-PaseoAgents.ps1`.

## Duplicate workspace records on one path (location activation stalls)

A workspace record is bound to a path, and a path can accumulate MANY of them:
`paseo run --new-workspace local` mints a record on every call, so a retry loop
on a failing location multiplies records. Past the first, the daemon cannot tell
which record is live and the location never activates:

```
OpenCode location E:\Repos\cl-common\.worktrees\<lane> did not activate within 30000ms
```

The daemon log names the real first failure — `workspace-git-service` →
`WorkspaceGitWatcherSubscriptionTimeoutError` ("Watcher subscription for
<path> timed out after 10000ms"), then `provider-snapshot-manager` →
`OpenCodeLocationReadyTimeoutError` (readiness.js `waitForPlugins`). The location
is not slow: `opencode serve` boots in ~2 s under the same `OPENCODE_CONFIG`.

Measured 2026-11-02 (Paseo 0.14.0): 41 active records across 19 paths, of which
7 paths were duplicated and held 29 records — `.worktrees/merge-84m` 6,
`.worktrees/lane-worknow` 3, `.worktrees/lane-keycheck` 2, `.worktrees/lane-zzq`
2, and 10 on `upscale-havens/.worktrees/conf-onboarding-provisioning`; 7 further
records pointed at directories that no longer exist.

| Need | Command |
| :--- | :--- |
| Report duplicated / orphaned record paths | `pwsh -NoProfile -File vendor/cl-orchestration/cl-paseo/scripts/Get-PaseoWorkspaceRecordReport.ps1 [-Path <path>] [-Json] [-FailOnDuplicates]` |
| Stop a dispatcher minting more | `run-iqa-worker.ps1` reuses the path's record instead of creating one, and fails once, named (`LOCATION-ACTIVATION-FAILED`) with the duplicate count |

**There is no non-destructive removal.** `paseo workspace --help` offers
`create | ls | rename | archive | setup` only — no delete, no detach — and
`archive <workspace-id>` is "Archive a workspace and everything it owns", i.e. it
takes the workspace's agents with it; the CLI exposes no way to enumerate which
agents a workspace owns (`paseo ls --json` carries no workspace id), so no script
can prove an archive safe. Removing records is therefore a Paseo change or an
operator decision. In practice: move the lane to a fresh path (new path ⇒ no
duplicate) rather than trying to repair the poisoned one.

## Bootstrapping your own process

| Seam | Fires | Use it for |
| :--- | :--- | :--- |
| **Boot task** (`Paseo Boot Resume`) | boot + delay, no login needed | deterministic reconciliation, no Paseo internals |
| **Plugin `contribute()`** | plugin load, i.e. daemon start / `plugin reload` | in-product bootstrap; gets `server.on` / `server.before` / `server.handle` and a `PaseoApi` client in hook contexts. Plugins are trusted and unsandboxed. |
| **Workspace script** (`paseo.json` + `paseo script start`) | when started, or via `paseo workspace setup` | per-workspace dev servers, not boot work |
| **Schedule** (`paseo schedule create --cron/--every`) | cron only, **no boot trigger** | idempotent reconcilers that can afford to wait for the next tick |

Plugin lifecycle events available in 0.14.0 (`@getpaseo/plugin` server
lifecycle): `agent.created`, `agent.closed`, `agent.turn_started`,
`agent.turn_ended`, `agent.permission_requested`, `agent.permission_resolved`,
`agent.archived`, `workspace.created`, `workspace.archived`; interceptors
`before` `agent.create`, `agent.session_open`, `workspace.create`. **There is no
daemon-start event** — a plugin's `contribute()` running at load is the boot
seam, and it must spawn the CLI (or capture an API from the first hook) rather
than expect a startup callback.
